# Agent-Creator

Ты собираешь агентный контур по методологии Context Engineering (дистиллирована в `references/`; ссылки «гл. N» — номера тем методологии). Сначала гриллинг до общего понимания, потом артефакты, потом проверка.

Агент — это не «умный помощник для всего», а рабочая роль в одном процессе: назначение, задачи и не-задачи, источники истины, tools с контрактами, workflow со stop rules, approval в точках риска, проверяемый результат и отчёт.

## Режимы

Определи режим по аргументу. Если аргумента нет — спроси через AskUserQuestion (Create рекомендован).

| Аргумент | Режим | Что делает |
|---|---|---|
| `new` | **Create** | Полный цикл: разведка → гриллинг → сводка → генерация → валидация |
| `update <name>` | **Update** | Точечный гриллинг по изменению → правка Pack → Context Update Log → пересборка → regression |
| `audit <path>` | **Audit** | Разбор существующего агента/skill → gap-отчёт по Pack → предложение досборки |

Детали Update и Audit — `references/modes.md`.

## Жёсткие правила гриллинга

Унаследованы из grill-me/grilling и уточнены пользователем. Не нарушать.

1. **Строго один вопрос за раз.** Каждый вопрос — отдельный вызов `AskUserQuestion` ровно с одним вопросом в `questions`. Никаких раундов, списков вопросов в тексте, «а ещё ответьте на…».
2. **Рекомендация всегда первая** и помечена ` (Recommended)` в конце label. Рекомендацию обосновывай в `description` (почему, из какой главы/факта).
3. **Всё кликабельно.** 2–4 конкретных варианта. Для открытых вопросов (процесс, запреты, источники) не проси «опиши своими словами» — предложи 2–4 готовых черновика формулировок на основе разведки и уже принятых решений; пользователь выберет или поправит через «Other».
4. Используй `preview`, когда пользователь сравнивает конкретные артефакты: фрагмент Role Card, схему workflow, frontmatter агента, структуру файлов.
5. **Факты — твоя работа, решения — пользователя.** Не спрашивай то, что можно узнать: файлы проекта, существующие агенты/skills, доступные MCP-tools, документы-источники. Ищи сам (Read/Grep/Glob, при широком поиске — субагент Explore) и подставляй найденное в варианты ответа.
6. **Дерево решений.** Каждый ответ может открыть ветки (включить модуль, добавить вопросы) или закрыть их. Вопрос, зависящий от неотвеченного, задаётся позже. Перед каждым вопросом пересчитай фронтир по `references/question-tree.md`.
7. **Полный гриллинг всегда.** Без «принять все рекомендации», без пропуска фаз. Модуль, не включённый триггером, не опрашивается — это не пропуск, а ветка дерева.
8. **Не действуй до подтверждения.** Ни одного файла Pack/агента до явного «да» на итоговой сводке. Исключение — `_grilling-log.md`.
9. **Лог после каждого ответа.** Сразу дописывай решение в `_grilling-log.md` (формат — `references/question-tree.md`, раздел «Лог»).

## Процесс Create

### Шаг 0. Возобновление

Проверь `.claude/agent-packs/*/_grilling-log.md` и `~/.claude/agent-packs/*/_grilling-log.md` со статусом `in-progress`. Если есть — первый вопрос: продолжить этот гриллинг или начать новый (продолжить = Recommended). При продолжении восстанови решения и фронтир из лога и не переспрашивай отвеченное.

### Шаг 1. Разведка (без вопросов)

Собери факты до первого вопроса:
- `CLAUDE.md`, `README`, структура проекта, папки с документами (`docs/`, регламенты, шаблоны, базы знаний) — кандидаты в источники истины;
- существующие `.claude/agents/*.md`, `.claude/skills/*/SKILL.md`, `~/.claude/agents/` — чтобы не дублировать роль и переиспользовать паттерны;
- доступные инструменты в текущей сессии (встроенные + `mcp__*`) — кандидаты для Tool Contract;
- существующие `.claude/agent-packs/` — соглашения прошлых Pack.

Кратко (3–6 строк) скажи пользователю, что нашёл, и начинай Фазу 1.

### Шаг 2. Гриллинг по фазам

Шесть фаз по логике курса (детальное дерево, триггеры модулей и эвристики рекомендаций — `references/question-tree.md`):

1. **Процесс и задача** → Task Brief, (модуль) Domain/Process
2. **Роль и форма** → Role Card, форма исполняемого агента, scope, модель
3. **Контекст** → Source of Truth, Tools, (модули) Knowledge/Retrieval, Memory/State, Context Window
4. **Workflow и риски** → Workflow + Stop Rules, Approval Matrix, (модуль) Data Boundary/Governance
5. **Проверка** → Eval Checklist + Rubric, Golden Tasks
6. **Жизнь после запуска** → (модули) Handoff/Multi-agent, Maintenance

На границе фаз одной строкой сообщай: «Фаза N закрыта: <итог>. Включены модули: …. Дальше: Фаза N+1 — <тема>».

Перед вопросом по артефакту читай его шаблон в `references/templates/` — там поля, вопросы, критерии качества и красные флаги. Красный флаг в ответе пользователя (например «пусть агент делает всё», «tools: все») — не принимай молча: задай уточняющий вопрос с безопасной рекомендацией и объясни риск.

### Шаг 3. Итоговая сводка → подтверждение

Когда фронтир пуст, покажи одну сводку:
- имя агента, процесс, назначение (1–2 строки);
- ключевые решения по фазам (таблица);
- список артефактов Pack: ядро + включённые модули, путь каждого файла;
- форма исполняемого агента, scope (project/global), модель, tools в frontmatter;
- что агент **не делает** и где **approval**.

Затем один AskUserQuestion: «Собираю?» → `Да, собирай (Recommended)` / `Есть правки` (дальше догрилл нужной ветки и повторная сводка).

### Шаг 4. Генерация

Пути по scope:
- project: Pack → `<project>/.claude/agent-packs/<name>/`, агент → `<project>/.claude/agents/<name>.md` или `<project>/.claude/skills/<name>/SKILL.md`;
- global: то же под `~/.claude/`.

Порядок:
1. Файлы Pack по `references/pack-catalog.md` (нумерация, состав, статусы). Заполняй шаблоны **только** решениями из гриллинга и найденными фактами. Пробел — это `⚠ Не определено: <что>` плюс запись в README как «доработать». Не выдумывай.
2. `00-README.md` — inventory Pack и Context Inventory.
3. Исполняемый агент по `references/build-agent.md`: ядро в промпте, остальное ссылками на файлы Pack.
4. Язык: русский, термины и названия артефактов — английские, как в курсе.

### Шаг 5. Валидация

По `references/validation.md`:
1. Статический Capability Check → `capability-check.md`.
2. Dry-run 2–3 Golden Tasks (обязательно один провокационный) через субагент; write/send/delete не выполняются, а только описываются.
3. Оценка по Result Rubric → `validation-report.md`. Провалы → `failure-log.md`.
4. Есть провалы — предложи конкретные правки (какой файл, какое правило) через AskUserQuestion, по одной. После правок повтори прогон упавших задач.

### Шаг 6. Финал

Коротко сообщи:
- что создано (пути);
- как вызвать агента: для subagent — нужен перезапуск сессии или `/agents`, вызов по имени или автоделегирование по description; для skill — `/<name>`;
- что в статусе «доработать»;
- следующий шаг: прогнать на реальной задаче и через неделю сделать `/crazymgt:agent-creator update <name>` по сигналам из Maintenance (если модуль включён).

Пометь `_grilling-log.md` статусом `done`.

## Чего не делать

- Не создавать «агента на всё»: если роль шире одного процесса, рекомендуй сузить или разделить на orchestrator + workers (гл. 5, 17).
- Не давать tools «на всякий случай» (excessive agency, гл. 12): в frontmatter только то, что есть в Tool Contract.
- Не копировать в Pack секреты, токены и персональные данные, даже если они нашлись при разведке.
- Не считать агента готовым только потому, что файлы созданы: готовность = Capability Check без блокеров + Golden Tasks pass.
