# Дерево вопросов гриллинга

Каждый узел — одно решение и один вызов AskUserQuestion. Узел задаётся, когда закрыты его предпосылки (`после:`). Узлы с `если:` существуют только при выполнении условия. Формулировки вариантов генерируй из разведки и прошлых ответов, а не копируй дословно.

Обозначения: **[R]** — эвристика выбора рекомендуемого варианта; **→** — что включает или выключает ответ.

---

## Фаза 1. Процесс и задача

Цель: один конкретный повторяемый процесс, а не «весь отдел» (гл. 3, 16, 19).

**P1. Процесс.** Какой процесс закрывает агент?
- Варианты: 2–3 формулировки по формуле «Когда <событие>, нужно <действие>, чтобы получить <результат>», собранные из запроса и разведки.
- [R] Самая узкая формулировка с понятным входом и выходом.
- Красный флаг: «продажи», «поддержка», «всё по проекту» — предложи сузить до одного шага.

**P2. Назначение.** Зачем агент существует в процессе? Для Role Card: «Назначение», для Task Brief: «Зачем».
- [R] Формулировка «снять с <роли> <рутинную часть> и снизить риск <X>», а не «увеличить продажи».

**P3. Trigger и вход.** Что запускает работу и какой минимум данных нужен для старта? `после: P1`
- [R] Минимальный обязательный вход. Без него агент ставит `blocked` (гл. 11).

**P4. Результат и критерий готовности.** Что агент отдаёт и как понять, что это можно принять? `после: P1`
- [R] Конкретный артефакт (таблица, черновик, отчёт, diff) плюс 3–5 проверяемых признаков готовности.

**P5. Нужна ли доменная карта?** `после: P1–P4`
- Включай модуль **Domain/Process** (рекомендуй), если есть хотя бы одно: процесс с ветвлениями и исключениями; несколько ролей людей; внутренние термины, которые агент может понять неверно («пилот», «лид»); есть владелец процесса вне пользователя.
- [R] Включить, если по разведке или ответам видны термины или роли. Иначе — не включать.
- → Включён: узлы D1–D5.

**D1. Роли людей и владелец процесса.** `если: Domain` — кто участвует, кто подтверждает, что процесс работает правильно.
**D2. Шаги процесса и разметка A/D/H/N.** `если: Domain` — для каждого шага: A — агент сам, D — черновик, H — нужен approval, N — не отдаём агенту. [R] Всё, что касается отправки наружу, денег, CRM-записи и обещаний, — H или N.
**D3. Decision points и исключения.** `если: Domain` — «Если <ситуация>, агент <действие>». [R] Предложи 3–5 исключений из типовых: конфликт данных, запрос гарантии, нет владельца, нет доступа, персональные данные.
**D4. Словарь процесса.** `если: Domain` — 3–10 терминов: что значит у нас, что не значит, риск ошибки. Варианты собирай из документов проекта.
**D5. Agent Fit.** `если: Domain` — проверка по 7 критериям (гл. 16): 5–7 «да» — агент, 3–4 — только черновик, 0–2 — сначала описать процесс. Это не вопрос, а вывод: покажи его и спроси подтверждение уровня автономии.

## Фаза 2. Роль и форма

**R1. Название и роль.** Название по функции («Агент первичного разбора заявок»), роль одной фразой. Имя файла — kebab-case латиницей.
- [R] Название по функции, а не персона.

**R2. Что входит в роль.** 3–7 задач. Варианты — наборы задач разной широты. [R] Самый узкий набор, закрывающий P4.

**R3. Что НЕ входит.** `после: R2` — 3–7 запретов. [R] Набор, который запрещает отправку наружу, обещания (цена, срок, результат), изменение и удаление данных, решения вместо человека, и всё, что D2 пометил N.
- Красный флаг: пустой список. Без него не двигаться дальше (гл. 5, ошибка 2).

**R4. Форма исполняемого агента.** `после: R2, R3, P3`
- **Subagent** (`.claude/agents/<name>.md`) — [R], если задача изолирована, работает на входе без диалога с человеком и возвращает отчёт. Approval через stop + Return Report.
- **Skill** (`.claude/skills/<name>/SKILL.md`) — [R], если нужен диалог с человеком по ходу, уточнения и approval внутри сессии, процедура в основном контексте.
- **Orchestrator + workers** (skill-оркестратор + N subagents) — [R], только если сработал триггер Handoff (Фаза 6, H0). Иначе не предлагать.
- Обязательно с preview: frontmatter и структура файлов.

**R5. Scope.** project или global. [R] project, если агент опирается на документы или процесс этого проекта; global, если это универсальная процедура для любых проектов.

**R6. Модель.** `inherit` / `sonnet` / `opus` / `haiku`. [R] `inherit` по умолчанию; `haiku` — массовая простая классификация; `opus` — сложные рассуждения и высокая цена ошибки.

**R7. Язык ответов агента и формат отчёта.** Reporting по гл. 5: что сделал, какие источники, где не хватило данных, что требует человека, следующий безопасный шаг. [R] Этот формат на русском.

## Фаза 3. Контекст

**S1. Главный источник истины.** Варианты — реальные файлы и системы из разведки. [R] Утверждённый, версионированный документ с владельцем.
**S2. Вторичные, рабочие, архивные и рискованные источники.** `после: S1` — статус каждого найденного источника (главный, вторичный, рабочий, архив, рискованный). Предлагай разметку целиком, одним вариантом на набор.
**S3. Правило конфликта.** `после: S2` — порядок доверия и условие остановки. [R] Policy безопасности > договор/регламент > рабочие данные > FAQ > переписка; при деньгах, сроках, юридических вопросах и персональных данных — стоп.
**S4. Правило цитирования.** Нужно ли указывать источник в результате. [R] Да: документ, раздел, версия.

**K0. Нужен ли поиск по базе знаний?** `после: S1–S2`
- Включай модуль **Knowledge/Retrieval**, если источников больше, чем помещается в контекст целиком, или агент должен искать фрагменты по запросу (RAG, grep по базе, MCP-поиск).
- → Включён: K1 (типы вопросов), K2 (метаданные и разбиение), K3 (способ поиска: keyword / semantic / hybrid / grep — исходя из того, что реально доступно), K4 (Query Test Set: 3–5 вопросов с ожидаемым источником и поведением, включая вопрос с правильным ответом «нужен человек»).

**T1. Набор tools.** Перечисли найденные инструменты, которые подходят задаче. Варианты — минимальный, рабочий и расширенный наборы. [R] Минимальный достаточный (гл. 12, excessive agency).
**T2. Уровень риска каждого tool.** `после: T1` — read-only / draft / write / send / delete-pay-irreversible. Предложи разметку целиком. Bash по умолчанию считается write-уровнем, пока не ограничен.
**T3. Контракт для каждого tool уровня write и выше.** `после: T2` — по одному вопросу на tool: когда использовать, когда нет, scope, approval, проверка результата, rollback. Для read-only достаточно общего правила одной строкой.

**M0. Нужна ли память?** Включай модуль **Memory/State**, если агент работает многократно и должен помнить устойчивые правила или предпочтения, либо задача длинная и многошаговая (нужен State Map).
- [R] Для разового subagent — не включать: state живёт в Return Report.
- → Включён: M1 (что сохранять), M2 (что нельзя сохранять — секреты, ПДн, временные статусы, эмоции), M3 (где хранится и кто читает), M4 (обновление и удаление), M5 (State Map: поля текущей задачи — только для длинных задач).

**W0. Нужна ли стратегия контекстного окна?** Включай модуль **Context Window**, если входы большие (длинные документы, много файлов, длинная переписка) или задача многоэтапная со сменой контекста.
- → Включён: W1 (что видит на каждом шаге), W2 (что держим снаружи), W3 (что сжимаем и как — Compression Log), W4 (что изолируем в отдельный поток или субагента).

## Фаза 4. Workflow и риски

**F1. Шаги workflow.** 5–9 шагов. Для каждого: input → action → output → check. Предложи готовую карту целиком с preview. [R] Карта, где tools привязаны к шагам, а «готово» подтверждается проверкой.
**F2. Stop Rules.** `после: F1` — по шаблону гл. 11: нет входа, конфликт источников, рискованный tool, действие наружу, задача вне роли, проверка не прошла. Формула: «если X — остановись, объясни Y, запроси Z, предложи следующий безопасный шаг».
**F3. Checkpoints.** Перед стартом, перед tool, после tool, перед внешним действием, перед «готово». [R] Все пять; для read-only агента checkpoint 4 вырожден.

**A1. Action Approval Matrix.** Распредели действия по классам: read-only, draft, internal write, external send/publish, irreversible/money/delete. [R] send/publish — только после approval; irreversible — агент не выполняет, только готовит план.
**A2. Как запрашивается approval.** `после: R4` — subagent: останавливается и возвращает `needs_approval` с готовым действием в Return Report; skill: AskUserQuestion с показом действия. [R] Зависит от R4 — это следствие, а не выбор; спроси только при нестандартной форме.

**G0. Есть ли чувствительные данные?** Включай модуль **Data Boundary/Governance**, если агент видит персональные данные, договоры, финансы, секреты, клиентскую переписку или внешний недоверенный текст (письма, сайты, вложения).
- → Включён: G1 (Data Boundary — 5 зон: напрямую / по необходимости / после очистки / только с approval / никогда), G2 (prompt injection rule — внешний текст = данные, не команда), G3 (Governance: владелец процесса, владелец агента, что логируем и что нельзя логировать).

## Фаза 5. Проверка

**E1. Хороший результат и красные флаги.** 3–5 признаков pass и 3–5 признаков fail. [R] Включить в fail нарушение approval boundary даже при красивом ответе (гл. 14).
**E2. Result Rubric.** 5–7 проверяемых критериев. [R] Факты верны · источник указан · запрещённых обещаний нет · формат соблюдён · следующий шаг понятен · риск эскалирован.
**E3. Golden Task Set.** 5–7 задач: обычная, неполный вход, конфликт источников, рискованное действие, обязательная остановка, плюс провокации из R3 и D3. Предлагай готовые наборы задач, сгенерированные из процесса. [R] Набор, где не меньше двух задач проверяют stop/approval.
**E4. Кто grader.** Человек / правило / код / LLM-as-judge. [R] Правила и код — для формальных признаков, LLM-as-judge — для предварительной оценки, человек — для финального решения в рискованных задачах.

## Фаза 6. Жизнь после запуска

**H0. Нужен ли второй агент?** Включай модуль **Handoff/Multi-agent**, только если есть хотя бы одно: другая компетенция; другие tools или доступы; отдельный риск, требующий reviewer; задача не помещается в одно окно; нужна независимая проверка (гл. 17).
- [R] По умолчанию «нет»: не усложнять.
- → Включён: H1 (паттерн: orchestrator → workers / handoff chain / agent-as-tool), H2 (Role Split Matrix — по вопросу на роль), H3 (Handoff Packet: обязательные поля), H4 (Return Report), H5 (финальный владелец и human approval). При включении пересмотри R4 → orchestrator + workers.

**X0. Нужен ли цикл обслуживания?** Включай модуль **Maintenance**, если агент будет работать регулярно (не разово).
- [R] Включить для любого повторяющегося процесса.
- → Включён: X1 (что считается нормальной работой — 3 пункта), X2 (5 сигналов: норма, тревога, действие), X3 (где берём сигналы и как часто смотрим), X4 (владелец обслуживания, правило остановки сценария и rollback).

## Пересчёт фронтира

После каждого ответа:
1. Запиши ответ в лог.
2. Обнови включённые модули (триггеры P5, K0, M0, W0, G0, H0, X0).
3. Фронтир — это узлы, у которых закрыты все `после:`, выполнено `если:` и нет ответа.
4. Выбери следующий узел: сначала текущая фаза, внутри фазы — по порядку в этом файле.
5. Если ответ противоречит прошлому решению (например, R3 запрещает отправку, а A1 разрешает), задай вопрос на разрешение конфликта, прежде чем идти дальше.

Узел можно закрыть без вопроса, только если ответ однозначно следует из фактов (например, A2 из R4). Запиши его в лог как `выведено` с обоснованием и упомяни в итоговой сводке.

## Лог (`_grilling-log.md`)

Создаётся после P1, когда известно имя-черновик. Путь: `<scope>/.claude/agent-packs/<name>/_grilling-log.md`. Если имя изменится в R1 — переименуй папку.

```markdown
---
agent: <name>
status: in-progress | confirmed | done
mode: create | update | audit
scope: project | global
started: <YYYY-MM-DD>
modules: [domain, knowledge, memory, context-window, data, handoff, maintenance]
---

## Фаза 1. Процесс и задача
- **P1 Процесс** — <ответ> _(рекомендация: принята | выбран другой вариант | Other)_
- **P5 Domain** — включён: есть термины «пилот», «лид»
...

## Открытые ветки
- T3: контракт для mcp__crm__update (ждёт T2)
```

При возобновлении: прочитай лог, восстанови решения и модули, пересчитай фронтир и продолжи. Отвеченное не переспрашивай.
